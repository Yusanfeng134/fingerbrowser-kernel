# 验证脚本

`patches-151/` 里每条补丁的提交消息都写着「验证通过」，这些脚本就是那句话的依据。
此前它们只存在于一台开发机上、未被任何仓库跟踪 —— 补丁可以重建内核，却无法重建
「凭什么认为它是对的」。

## 为什么每个脚本都带反例或前提检查

这批脚本反复被同一类问题咬：**通过条件被一个与被测对象无关的前提满足了**。实际
发生过的：

- 补丁 19 个全部干净应用，树却差两行 —— 只看「应用成功」会漏
- AI 新标签页正常打开，但地址栏是只读的 —— 只看「页面出来了」会漏
- 面板「设置」项能打开一个标签页，只是去错了地方 —— 只看「能点开」必然通过
- 白名单没有反例可测时，「链接都能打开」与「白名单形同虚设」表现完全一致
- 固定标签清理：复现失败时「只剩一个标签」与真的修好长得一模一样
- `getVoices()` 首次返回空数组，被当成「没有 CJK 语音」——稳定的假阳性

所以：**只验「能做到」不够，必须同时验「不该做到的做不到」**。

## `STALE` 检查

**启动内核的** `.cjs` 开头都检查 `D:/yunbrowser-run/STALE`。构建成功但同步失败时
会留下该标记，探针拒绝运行 —— 否则会在旧内核上得出结论。这事真实发生过一次，
让用户白测了两轮。

一个例外：`run-island-query.cjs` 不检查，因为它**不跑内核**，只读源码求值。给它
加上 STALE 检查会让它在一次纯注释改动导致的同步失败后无谓地拒绝运行（这已经
发生过）。

但这个例外有代价，用它的时候要记住：**它通过不代表你正在跑的内核里那行是对的**
—— 源码和已同步的二进制可以不一致，而这个脚本只看得见前者。要断言运行中的内核，
得用启动内核的那一类。

标记本身有过两个洞，都已修：第一版写在「内核是否在跑」检查之后（最常发生的那种
失败恰好不留标记）；构建失败时同步脚本根本不被调用（由 `build-and-sync.sh` 自己
补写）。

> 一道正好漏掉主要失败模式的防线，比没有更糟 —— 它在其余场景里正常工作，持续
> 提供「已经防住了」的证据。

## `run-webgl-params.cjs` 为什么没有对应补丁

它得出的结论是**不该做那件事**。

原以为 WebGL 参数（`MAX_TEXTURE_SIZE` 等）未伪装是个缺口。实测：伪装 GPU 字符串
后，25 个参数、35 个扩展、着色器精度**全部不变**；而这些值是 ANGLE/D3D11 按特性
等级归一化的，不随厂商变 —— 一块真实的 Intel UHD 620 在同一后端下报同一组数字。

又查了 `gpu_driver_bug_list.json`：Windows 上仅 2 条禁用扩展的规则，均不按厂商
匹配。所以扩展列表也不泄漏厂商。

**给这些参数加开关反而更糟**：客户端填一个与所声称 GPU 不符的值，就把「未伪装」
换成「矛盾」，而未伪装在这里本来就不成立。净效果是引入一个只会造成伤害的旋钮。

改为守一条不变量：厂商词只允许出现在 `unmaskedVendor` / `unmaskedRenderer` 里。
这条不锁具体数值（ANGLE 升级会改），但将来某版本开始暴露厂商专属参数或扩展时它
会响。

## 已知限制

- 路径硬编码为 `D:/chromium-work-151` 与 `D:/yunbrowser-run`，换机器需改。
- 地址栏、菜单启用状态是浏览器原生 UI，CDP 读不到，那几条只能人工确认。脚本里
  已标明哪些是程序验的、哪些不是 —— **不拿「脚本没报错」冒充通过**。
- `run-creepjs-audit.cjs` 的 TTS 一项在无语音包的机器上无法判定，此时明确输出
  「无法判定」，不计入通过。
