## 3. 三个生成上的决定

**按纯净 151 做累积全文件 diff**，与 `gen-patches-151.sh` 一致，不是逐提交 `format-patch`。
因此**同一个文件只能出现在一个补丁里**，否则后一个会把前一个的改动再带一遍。

**品牌文案排在最前（0014）**：`chrome/app/generated_resources.grd` 同时承载侧栏的字符串
与品牌改名，按文件切不开，只能落在一个补丁里。放在侧栏（0016）之前，0016 应用时字符串
已经就位。

**侧栏 / 垂直标签栏 / 开关拆分合成一个补丁（0016）**：侧栏的 coordinator 与 WebUI 也被
「外壳与伪装拆成两个开关」那次改过，`features.cc` 被两次垂直标签栏提交改过 —— 按文件切
不开。

**0017 的 diff 范围截到 `0f7cbd0ae9`，不是 HEAD**：`startup_browser_creator_impl.cc`
之后还被你的「清理遗留固定标签」改过，用 HEAD 会把那段一起带进来，导致你的补丁重复应用。

**0015 用 `--binary`**：`.ico` 不加这个开关时 git 只写一行 `Binary files differ`，
补丁能应用但图标不会变 —— 正是你说的那种「装得上却什么都没做」的补丁。

## 4. 我验了什么、没验什么

**验了**：

- **覆盖完整**：分支相对纯净 151 改动的 265 个文件，现在 265 个都被补丁覆盖，无遗漏、无多余。
  （`.ico` 在这个统计里要单独看：二进制 diff 没有 `+++ b/` 行，靠 `GIT binary patch` 段确认。）
- **文件集重叠只剩既有的分层**：0003/0013、0009/0011、0013/0014 是你们原有的按提交分层，
  加上新的 0017/0019 一处 —— 都靠顺序解决。
- **最关键那条端到端跑通了**：把纯净 151 的 `startup_browser_creator_impl.cc` 取出来，
  依次应用 0017 与你的清理补丁，结果与分支 HEAD **逐字节一致**。这正是之前卡住的那条路径。

**没验**：整套 0001–0019 应用到纯净 151 后与分支 HEAD 的**全树逐字节比对**。那需要一份
干净的 151 检出，成本在你那边更低，你也已经提出要跑这一遍。在那一步通过之前，
**不要把「补丁全部干净应用」当作「内核可从纯净 151 重建」** —— 这条 README 里原来的
警告仍然成立，只是缺口从「210 个文件没导出」变成了「导出了但未做全树验证」。


## 5. 修订（2026-07-29，全树比对之后）

内核会话跑完 0001–0019 的全树逐字节比对，19 个补丁全部干净应用，但结果树与 HEAD 仍差
**两行**，在 `chrome/browser/ui/BUILD.gn`：Voyager 侧栏的两条依赖。

**根因是第 3 节那条「同一个文件只能出现在一个补丁里」有个隐含前提：一个文件的全部改动
来自同一方。** 这个文件不满足 —— 它同时被 0013（地址栏）和侧栏工作改过。生成器看到它
已被 0013 认领就跳过，于是侧栏那两行不在任何补丁里。两边各自都对，合起来漏了一块。

这一漏的症状在**链接期**：`VoyagerSidePanelUIConfig` 的构造函数找不到 —— 看起来像代码
写错了，真实原因在补丁集里。

**已修**：0016 追加一个针对该文件的**增量** hunk（「0013 应用之后 → HEAD」），而不是把
整个文件的累积 diff 塞进去 —— 后者会把 0013 那行重复带一遍。0016 在 0013 之后应用，
上下文对得上。

生成脚本已同步，重新生成可复现（幂等：先覆盖写 0016，再追加该增量）。已验证：
纯净 151 → 0013 → 0016，该文件与分支 HEAD 逐字节一致。

**这条规则以后要这样用**：分配文件前先看它是否被多方改过；是的话不能整file归属，
只能按「后应用方生成增量」处理。
